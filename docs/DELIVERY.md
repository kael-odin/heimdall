# 交付：三种产物、一条判据

> 这份文档回答三个问题：**静态镜像与交互镜像各自的价值是什么、交付包为什么是另一个层次的东西、
> 以及"重新导出"和"给已部署的包打补丁"该选哪个。** 全部结论都对应到代码里的实现，
> 没有实现的部分明确标为"未做/不做"。

---

## 1. 第一性原理：一个词"克隆"其实在解三个不同的题

要设计产物，先要承认需求不是一种：

| 谁 | 想干什么 | 需要什么性质 |
| --- | --- | --- |
| 产品 / 运营 / 评审 | 看清原站**现在**是什么样、怎么用 | **活**的：能点、能搜、跟着原站走 |
| 前端工程 | 拿它当**视觉基线**做还原 | **冻结**的：同一份产物两次必须得到同一个结论 |
| 同事 / 客户 | 拿走、部署、自己验证 | **自包含**的目录；离线完整度须按 strict 检查与浏览器验收确认 |

由此得到一条判据，它决定了后面所有的取舍：

> **会变的东西不能当基线；需要跑起来的东西不能当交付物。**

于是产物必须分三层，而不是"一个好一个差"：

| 产物 | 一句话 | 满足上表哪一行 | 代码 |
| --- | --- | --- | --- |
| **静态镜像** | 渲染结果冻结成的静态文件 | 第 2 行 | `crawler/capture.mjs` + `crawler/build_clone.mjs` |
| **交互镜像** | 页面照常运行脚本，资源实时回原站 | 第 1 行 | `crawler/build_live.mjs` + `engine-server.mjs` 的镜像路由 |
| **交付包** | 一个可执行目录，同时装下前两者 | 第 3 行 | `live/export.mjs` + `live/serve.mjs` |

---

## 2. 静态镜像：为什么必须是"照片"

三条理由，每条都对应代码里的一个机制：

1. **打分要求可重复。** 保真度分数（`differ/diff.mjs`）是"同一页、同一视口、两次独立渲染"的像素差。
   如果产物自己在动，分数就变成了噪声的度量。所以 capture 会注入冻结策略：
   CSS 动画/过渡时长归零、轮播回初始位、输入框清空（`crawler/capture.mjs` 的 `FREEZE_CSS`）。
2. **归因要求"只差一处"。** 剥离脚本之后，剩下的差异只可能来自样式、结构、资源，
   于是差异可以被分类：集中在某块（少了一张图）还是弥散（字体抗锯齿）。
   带着脚本的产物做不到这件事 —— 差异会混进"JS 有没有跑完"这个噪声里。
3. **离线要求自包含。** 评审现场可能没网、原站可能已经改版甚至下线。静态镜像以本地可开为目标，资源缺口需逐页检查。

代价也是明确的：静态镜像不保留原站 JS 交互和实时数据；CSS 动效与部分已捕获关键帧可重演，其余停在捕获帧。

---

## 3. 交互镜像：价值是"能验证功能"，不是"更好看"

有些东西静态镜像**原理上**拿不到：WebGL / canvas 渲染、无限滚动、登录后的页面、
实时价格、表单提交、客户端路由。交互镜像的价值是"**这个功能到底能不能用**"，
而不是"看起来像不像"——它的视觉是原站自己的，没有经过我们的校准。

引擎运行时仅通过独立镜像域名打开，避免源站脚本在引擎 API 主域执行：

| 入口 | 形如 | 何时用 |
| --- | --- | --- |
| 独立域名 | `http://<host>.localhost:<port>/<path>` | 引擎入口：pathname 就是站点自己的路径，CSR 路由/登录态/本地存储按站点隔离 |
| 路径前缀 | `/lm/<host>/<path>` | 仅独立交付包的 `serve.mjs` 提供；引擎主域返回 410 |

**已知边界**：独立包的路径前缀会被纯客户端渲染站点的路由当成真实路径（它会渲染自己的 404）。
这条的来龙去脉见 [历史 HANDOFF](archive/HANDOFF-through-2026-10-13.md) §25。
引擎启用 Token 时，控制台通过短期单次票据进入独立镜像子域；票据兑换后地址回到原站路径。跨主机控制台用带 Token 的 API 请求领票。独立交付包不依赖引擎 Token，部署前仍要单独验收权限、Cookie 和数据分发边界。

静态克隆在新构建和重新导出时会净化源站事件处理器与脚本入口；独立服务对静态 HTML 另加浏览器沙盒。历史 `core/workspace/` 文件和已存在的交付包不会自动改写，旧包需重新导出并逐包检查后再分发。

## 4. 交付包：不是"第三种镜像"，是另一个层次

交付包 = `DATA_ROOT/deliverable/<host>-live-<date>/`，内容是：

```
serve.mjs / har.mjs        零依赖 Node 服务器（不装任何东西就能起）
heimdall-live.json         配置（host/origin/port/offline/replay）
har.json                   清洗后的 HAR（**不含 cookie/authorization/set-cookie**）
site/live/**               交互镜像页面
site/static/<host>/**      静态镜像页面 + 档案 + 对比 + SEO 报告
landing.html               落地页（镜像 / 档案 / 报告的入口）
health.json                离线体检：资源 local/HAR/unresolved、未镜像链接
checksums.json             每个文件的校验和
Dockerfile / docker-compose.yml / README.md
```

**为什么它是另一个层次**：前两种产物的判据是"像不像 / 能不能用"，
交付包的判据是"**能不能在另一台机器上跑起来，并让接收方核对离线资源与功能边界**"。
`checksums.json` 与 `health.json` 就是为此存在的 —— 接收方不必相信我们的口头结论。

**实测**（2026-10-11）：`node src/live/export.mjs ant.design` → 75 文件 / 3.2MB，
起 `node serve.mjs --port 8080` 后落地页 200、`/lm/ant.design/` 返回原站标题。
该站当时**只有 1 个克隆页、没有做过侦察** —— 也就是说"克隆一页也能交付"是成立的。

> **部署纯前端站点时必须 `--root mirror`**（镜像挂在根路径）。默认的 `landing` 模式
> 会把页面放在 `/lm/<host>/` 前缀下，接收方那边同样会落到该站自己的 404。
> 控制台导出走的就是 `--root mirror`。

## 5. 增量：为什么是"重新导出"，而不是"给已部署的包打补丁"

**结论：不做补丁协议。**

第一性原理是两条：

1. **补丁协议存在的理由是"数据不可重新生成"。** 镜像包恰好相反：
   原站还在 → 重新抓；原站没了 → 交互镜像里的 HAR 快照还在。
   我们所有的产物都满足"重放导出 = 全量"，也就是幂等。
2. **补丁要付的成本是实打实的**：版本协商、部分失败的原子性、回滚、以及"接收方改过文件怎么办"。
   而重放导出的成本是一次 CPU 时间（单页 3.2MB、整站几十页）。

所以正确的做法不是发明协议，而是**把"增量"降到传输层**，我们只需要提供三件东西：

| 想要的"增量感" | 该怎么做 | 现状 |
| --- | --- | --- |
| 只传变化的文件 | **稳定输出目录**：`--out <dir>` 固定目标，接收方 `rsync`/`robocopy` 即可只同步变化的部分 | 参数已支持；控制台导出用的是按日期的目录 |
| 知道这次多了什么 | 导出一份**差异清单**（新增/变化/删除 vs 上一次导出） | **已实现**：`changes.json`（`src/live/changes.mjs`），控制台卡片直接显示 |
| 接收方能验真 | `checksums.json`（已有）+ `heimdall-live.json` 里的导出时间与 origin | 已有 |

`changes.json` 只是两个校验和列表做差集，**不含任何补丁语义**。
它有两个必须处理的细节，都写在 `changes.mjs` 的注释里：

- 上一次的校验和必须在**输出目录被清空之前**读 —— 同一天重导落在同一个目录，
  清完再读就只能和自己比（表现为永远"首次导出"）
- 四个根级元数据文件（`checksums/changes/health/heimdall-live`）带时间戳、每次必然不同，
  已排除在比较之外；否则用户每次都看到"变化 4"，真正关心的"页面变了没"被噪声淹没。
  `har.json` 记录的是本次抓取的请求时间，它报"变化"是正常的，`note` 里写明了

明确**不做**的：往已部署实例里逐层打补丁。除了上面两条理由，
还有一个现实原因：部署形态是多样的（Node 直跑 / Docker / 静态托管），
我们无法知道对方怎么部署，任何"打补丁"协议都会在第一台异构环境上失效。

## 6. 需要登录与鉴权的站点

### 6.1 第一性原理：身份到底存在哪里

抓得到什么，取决于"身份"以什么形式存在：

| 身份形式 | 例子 | 我们能不能复用 |
| --- | --- | --- |
| Cookie（含 session cookie） | 绝大多数站点 | ✅ `storageState.cookies` |
| localStorage（JWT 常见） | SPA 后台 | ✅ `storageState.origins[].localStorage` |
| sessionStorage | 少数 SPA | ✅ 源站采集时按完整 origin 恢复顶层标签页；同源多标签页差异不保留 |
| IndexedDB | 少数应用 | ✅ 源站采集时随 Playwright `storageState` 保存和恢复；实际登录效果仍需逐站验证 |
| HTTP Basic / Bearer 头 | 内部 API、沙箱 | ❌ 需要单独的请求头配置 |
| 客户端签名（时间戳 + 密钥） | 部分反爬 | ❌ |

### 6.2 我们的路线：人工登录一次，机器复用

`node core/src/session/login.mjs <host|url>`（控制台是本站操作里的「登录并保存会话」）会：

1. 打开一个**真浏览器窗口**访问该站点；
2. 人在窗口里完成登录 —— 验证码、短信码、扫码、第三方 SSO 都行；
3. 我们每 2 秒把 Cookie、localStorage、IndexedDB 和顶层标签页的 sessionStorage 存一次到 `workspace/<host>/session.json`（原子写）；
4. 之后的侦察 / 克隆 / SEO 审计 / 多视口验证在访问原站时自动恢复这些状态。

这只帮助采集端访问获授权的源站。导出包不包含 `session.json`，也不会因此拥有独立的登录、登出或账号服务。Service Worker 缓存、浏览器内存状态与同源多标签页的差异仍不在保存范围内。

**为什么不自动化登录**：每个站点的登录流程都不同，且几乎都有验证码或 2FA ——
自动化注定只对少数站点有效；而"绕过验证码"既不在我们的目标里，也不该做。

**安全**：`session.json` 等同凭据。它只落在本地 workspace（`.gitignore` 已覆盖，不进 git），
**不进交付包**（`live/export.mjs` 是白名单式拷贝），HAR 里的 cookie/authorization 也已被清洗。

### 6.3 今天能克隆什么、不能克隆什么

按能力盘点（证据在各文件的实测记录里）：

**今天就能克隆**：无登录、无硬 WAF 的 SSR / 静态 / 营销站 ——
React / Next / Vue / VitePress / Docusaurus / SvelteKit / Angular 的部分公开样本站已有历史克隆记录；当时的“8 站全 A”使用旧评分口径，尚未按 v2 和当前源站重算，不能视为现行质量保证。

**需要一点配置**：纯 CSR/SPA（要独立域名入口 + `--root mirror` 部署）；
含第三方挂件 / 懒加载 / 画布的站点（靠站点配方的剥除规则与滚动扫掠）。

**仍需逐站处理或暂不支持**：

| 能力或限制 | 当前情况 | 记录位置 |
| --- | --- | --- |
| 登录/付费墙后的内容 | 可人工登录后尝试采集，见 6.2；尚未在真实凭据站点验证，也不提供导出包的独立登录服务 | `RISKS.md` |
| Cloudflare / CAPTCHA 硬墙 | 代码里没有任何 stealth / 出站代理；实测过的站点都没撞上硬墙 | `RISKS.md` |
| WebGL 渲染 | 需要 `preserveDrawingBuffer`，现在只覆盖 2D canvas 光栅化 | `RISKS.md` |
| shadow DOM 内的样式 | 只处理 light DOM | [ROADMAP](ROADMAP.md) |
| iframe 内嵌内容 | 跳过不本地化（apify 的 YouTube 嵌入离线后为空） | [历史 HANDOFF](archive/HANDOFF-through-2026-10-13.md) §22.5 |
| HLS / 流媒体 | 无实现 | — |
| 无限滚动「加载更多」 | 只有定步长滚动扫掠 | [ROADMAP](ROADMAP.md) |
| A/B、地域、个性化内容 | 静态镜像剥脚本，交互镜像看到的是当前这一次 | — |

撞上硬墙时的正确做法是**换站或只做 SEO**，不是对抗 —— 这一点写在 `RISKS.md` 里。

## 7. 用户想做「竞品站」时，该给的是交付包吗？

**是，但要分清交付包给的是"起点"还是"成品"。**

用户的原话是：拿一个竞品站，替换里边的文字 / 图片 / logo / 文案，再接上自己的
后端与后台。这条路径我们确实支撑得住，而且是这个项目最实在的价值 —— 但要诚实
地说清楚它**到哪一步为止**。

### 7.1 交付包是"起点"，不是"成品"

交付包给的是：**在已采集和验收范围内可部署的视觉与结构基线**，连同它的
资源清单、健康报告、对比证据。用户拿到手之后要做的是"换内容、接后端"。

它给不了的、也不该由我们伪装成能给的是：

- **数据**：原站的商品/文章/价格是我们**抓下来的一份快照**，不是用户自己的
  CMS。替换内容意味着替换数据源，那是用户的后端该做的事
- **业务逻辑**：原站的登录、下单、购物车是它的后端。镜像只有静态渲染结果 +
  可选的原站 API 回放（`/px/` 代理，上线后回源）。这条边界必须写在眼里
- **版权**：这是**技术演示与自用改造的起点**，不是"换皮上线"的许可证。
  `RISKS.md` 里那条红线（只碰公开页面 / 有权访问的页面）依然成立

所以正确的说法是：**交付包 = 可部署的视觉与结构基线 + 一份诚实的资产账本**，
用户在这之上做内容与后端的替换。任何"一键生成竞品站"的暗示都是过度承诺。

### 7.2 这条路径上，我们做得好与不够好的地方

**已落地**：`edit-manifest.json/md` 汇总资源原始 URL、本地路径、引用页、类型与体积，也列出标题、H1、CTA、价格和域名出现位置；独立交付包自带这份清单和接手说明。控制台展示优先资源，可定位本地文件；域名替换先预览命中，再确认写入并逐文件备份。资产缺口扫描会在清单中注明扫描页数和截断状态。像素、DOM 与字段分数可辅助查问题，但旧单页分数和多视口 v2 不能混排。

**下一步**：

1. 把侦察、克隆、完整多视口测量、离线资源、动态交互的覆盖数汇成一页验收摘要；保留评分版本、失败原因与未测页，不让单个高分代替交付结论。
2. 用获授权站点验证资源与文案清单是否足够支撑接手者完成一次改版，并记录定位、域名替换和复验耗时。
3. `--strict` 已检查逐页首次加载；继续在真实断网浏览器中验收点击、表单、API、登录及长时间运行。未覆盖的流程仍可能需要回源或逐站实现。
