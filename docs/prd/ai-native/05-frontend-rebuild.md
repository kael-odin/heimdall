# 05 前端高精度重建

上一篇：[04 需求](04-requirements.md) · 下一篇：[06 逻辑补全与后端克隆](06-logic-backend.md)

本章是重建环（E6、E7）的技术方案：什么叫「高精度」、怎么把 GB 级产物压成模型能用的证据、怎么把视觉差异变成可操作的修复线索、怎么收敛、要花多少钱、哪些事做不到。

## 1. 门禁与口径

### 1.1 「高精度」不是一个数，是一张表

门禁是**合取**：每一维都要过，高分不能抵消低项（沿用验收子系统「视觉高分不会抵消菜单状态错误」的原则）。阈值为【假设】，Phase 0 用夹具校准（§1.4）。

| 维度 | 指标 | bronze | silver（默认） | gold |
| --- | --- | --- | --- | --- |
| **visual.pixel** | 每个视口的像素相似度（排除动态遮罩） | ≥ 0.95 | ≥ 0.97 | ≥ 0.99 |
| **visual.maxBlob** | 最大连通差异块占视口面积 | ≤ 1.5% | ≤ 0.5% | ≤ 0.2% |
| **visual.maxRegion** | 最大集中差异区域占视口面积（§1.2，Ph0 新增；阈值为【Ph0 建议值】） | ≤ 0.5% | ≤ 0.1% | ≤ 0.05% |
| **structure** | 语义清单相似度：地标、标题（级别 + 文本）、链接（文本 + 规范化 href）、图片 `alt`、表单控件（类型 + 标签） | ≥ 0.95 | ≥ 0.98 | ≥ 0.99 |
| **style** | 已对应元素中，关键计算样式偏差的元素占比 | ≤ 10% | ≤ 5% | ≤ 2% |
| **assets** | 断网加载零外联、本地资源零 4xx | 可选 | 必须 | 必须 |
| **health** | 无页面错误、无本地 4xx / 5xx、无横向溢出 | 必须 | 必须 | 必须 |
| **behavior** | 声明的流程全部通过（如有声明） | 必须 | 必须 | 必须 |
| **反作弊** | 候选不得引用 `.heimdall/ref/` 下的文件，不得以参考截图或整页位图充当内容（[E7-18](04-requirements.md)） | 必须 | 必须 | 必须 |

视口固定为 375×812、768×1024、1440×900，与验收和 `verify` 一致。**数值约定**：`pixel`、`structure` 写成 0–1 的比例；`maxBlob`、`style` 写成百分数，机器字段统一带 `Pct` 后缀（0–100），见 [附录 C §0](appendix-c-schemas.md)。

**Ph0 校准结论**（S1【实测】，两页 × 三视口，216 个单缺陷变体 + 12 个三缺陷变体，方法见 §1.4）：

- **页级像素和最大块基本看不见小缺陷**。silver 只判不过 40% 的注入缺陷，gold 48–50%。平移 2–8px、字号 ±2px、颜色变化让整页像素只掉约 0.01 个百分点，这三类被 silver 拦下的只有 6–17%。反过来，可接受的亚像素抖动（25% 的文字元素偏 0.5–1px）就要吃掉 0.2–0.9 个百分点。三处真缺陷叠加的一页仍有 99.3%，能过 gold 的像素线。
- **区域维度能分开两者**：「最大集中差异区域」= 对齐并做 ±1px 容差后、排除零散噪声的最大区域，占视口面积的百分数。

  | 阈值 | 注入缺陷检出 | 参考重拍误报 | 纯噪声误报（灰度文字） | 纯噪声误报（LCD 文字） |
  | --- | --- | --- | --- | --- |
  | 0.05% | 85–88% | 0 | 8% | 33% |
  | 0.1% | 78% | 0 | 8% | 17% |
  | 0.2% | 65% | 0 | 0 | 8% |

- **据此新增维度 `visual.maxRegion`**（【Ph0 建议值】，Bench v0 用真实重建样本复核）：bronze 0.5%、silver 0.1%、gold 0.05%，由 Heimdall 评估器在 `--disable-lcd-text` 下计算（§1.5）。像素与最大块保留，作粗门槛和历史可比的数字。
- **§1.4 的「检出 ≥ 95%、误报 ≤ 2%」在这批样本上做不到**。阈值 0.02% 时检出 93–95%，纯噪声误报 25–67%。不硬凑，以 Bench v0 的真实重建样本再定。

### 1.2 口径细则

| 指标 | 怎么算 | 复用 / 新增 |
| --- | --- | --- |
| pixel | `1 − 差异像素 / 并集面积`，pixelmatch threshold 0.1（`verify/compare.mjs` 的 `comparePngBuffers`，即验收正式裁判用的同一个函数，它在验收指纹冻结文件内）。**Ph0 改口径**：草案原定用 `differ/diff.mjs` 的「任一通道差 > 24」，S1 实测两种规则同一对图之差中位 0.3–0.4、p90 约 2、最大 3–4 个百分点；S4 实测用它会让快速裁判稳定偏离正式裁判 1.1–2.4 个百分点。`diff.mjs` 口径只留给旧的克隆评分 | 复用 |
| maxBlob | 对差异图做连通块分析，取最大块面积占比（`differ/shape.mjs` 的 `largest`） | 复用 |
| maxRegion | 修复包的最大集中区域占视口面积（行对齐 + ±1px 容差 + 排除零散噪声，§3.1），灰度文字拍摄 | 新增（Ph0 S1） |
| 动态遮罩 | 参考侧多帧之间的差集并集；遮罩占比写入报告，过大标 `needs_review` | 复用 `frame-*.png` 机制，新增遮罩导出 |
| structure | 语义清单做多重集合 F1 | 新增（验收的 DOM 语义检查是粗粒度的 pass/fail，不输出相似度） |
| style | 对应元素（§3.2）上比较 ~20 个计算属性，容差：长度 ±1px，颜色 ΔE ≤ 2 | 复用 `style-probe.mjs` 的属性清单，新增对应与容差 |
| assets | 候选页网络日志中无非本机 origin、无本地 4xx | 复用 `live/health` 的探针思路，新增 |
| health | 控制台错误、`pageerror`、失败请求、`scrollWidth > clientWidth` | 复用验收的健康检查口径 |
| behavior | 同一流程在参考与候选上执行，比较可观察结果 | 复用 `operation-plan` 语言，新增双侧回放（E8-03） |

**环境一致性**：参考截图是在克隆当时的机器上拍的。候选在另一台机器、另一套字体下渲染，抗锯齿差异会吃掉分数。参考包记录 Chromium 版本、操作系统、字体指纹；`compare` 发现不一致时告警，并建议在同一台机器上重拍参考（`heimdall brief --refresh-ref`）。

### 1.3 判定规则

- 一次运行内门禁配置**冻结**，哈希写入账本（E7-09）；模型改了配置，本次不生效并告警（E7-04）。
- 任何一维 `blocked`（缺测、执行上限、环境问题）整体不得通过；遮罩过大、参考不稳定标 `needs_review`。
- **只有正式裁判能宣布 `passed`**；快速裁判最好只给出 `pass-candidate`（[03 §5.5](03-architecture.md)）。

### 1.4 阈值怎么校准（Phase 0）

对三类样本分别求分布：①镜像自身（应接近 100%，用来量环境噪声）；②镜像 + 人工注入缺陷（位移 2–8px、字号 ±2px、颜色偏移、缺图、缺块）；③一份手写重建。再选阈值，使注入缺陷检出 ≥ 95%、误报 ≤ 2%。思路与 `acceptance:benchmark` 的 TP / FP / FN / TN 一致。校准结果回写本表，并更新所有引用（[10 §3](10-roadmap-risks.md) A-10、A-11）。

**Ph0 做了什么**（S1，【实测】，2026-10-25）：thordata.com 首页与 apify.com/about，三视口。

- **样本**：每视口 6 类缺陷 × 3 个实例，取自页面上、中、下三段。各类缺陷的具体形态：平移 0/3、6/0、8/8 px；字号 +2/−2/+2 px；颜色两处明显变化、一处 +28 的细微变化；缺图；缺块；`margin-top` 加 8/16/24 px。每个实例有「干净」与「带噪声」两个变体，噪声是 25% 的文字元素偏 0.5–1px。另有三缺陷混合变体。
- **噪声底**：参考重拍、复原后重拍两项，在两页三视口都逐像素一致（遮罩 0 px）。同一台机器上镜像的渲染是确定的。
- **样本③（手写重建）**由 S2 提供，结论见 [10 §3](10-roadmap-risks.md) A-1。

阈值结论见 §1.1 表后。

### 1.5 正式门禁的组成

验收 Mirror 只覆盖其中一部分，其余由 Heimdall 的确定性评估器补上，**两者合起来**才是 `heimdall.gate/1`。

| 维度 | 真值来源 |
| --- | --- |
| visual（整页像素、最大块、最大集中区域） | Heimdall 评估器：与快速裁判同一套代码和拍摄流程，灰度文字，超过 12,000px 的页面按 4096px 分块拍整页（沿用 `verify` 的 `tiled-compare`），像素口径同 `comparePngBuffers`。**Ph0 改**：验收 runner 的截图预算是高 12,000px、总量 1,200 万像素，thordata.com 首页三个视口全部超限，只拍首屏，视觉判 `needs_review`（S4）。这条预算在指纹冻结的 `runner.mjs` 里，不能改 |
| visual（首屏交叉核对）、structure（粗）、health、behavior 步骤 | 验收 Mirror 报告（`POST /api/acceptance/runs`；基线 = 镜像的正式基线副本，目标 = 候选） |
| structure（相似度）、style、assets | Heimdall 评估器（新代码，不在指纹冻结文件内） |
| **anticheat**（反作弊，E7-18） | Heimdall 评估器：源码引用 `.heimdall/ref/` 直接拒；候选页里占视口 ≥ 60% 的位图与参考整页 / 每条视口高横带做 8×8 均值哈希比对（汉明 ≤ 6/64 判命中）；参考可见正文在候选里的覆盖率 < 30% 判缺失。命中即整体不过，像素分不作数。**不比分段裁片**：hero 这类大图占满分段时，合规复用原件会和参考裁片几乎一样，比了会误判 |
| 合取与等级 | `Gate` 封装（新）：读取验收报告 + 评估器结果，写 `gate.json`，每项带证据引用和真值来源 |

**实现（2026-10-26，E7-06）**：`heimdall gate report --project .` 跑一次快速对比后组合 `heimdall.gate/1`：六维逐项给 `pass` / `fail` / `not_measured` 与实测值、阈值、差距；整体 `passed` 只在六维全过时成立，采集不到（例如单段范围没有正文覆盖率）记 `incomplete`，不冒充通过。阈值按 bronze / silver / gold 三档内置，可在 `heimdall.config.json` 的 `gate.thresholds` 里逐项覆盖。未通过时退出码 1，供 CI 与代理判断。**这份报告的 `passed` 是快速裁判口径**，只代表「按确定性规则没发现不合格」；对外宣布通过仍只由正式裁判（E7-07）给出。

**实现（2026-10-27，E7-07）**：`heimdall gate formal --project .` 把上面的六维与验收 Mirror 合起来判：正式基线 → `POST /api/acceptance/runs` → 轮询 → 报告；`acceptance` 作为第七维参与合取（`passed` / `failed` / `not_measured`）。只有七维全过才写 `status: "passed"`。基线在供出去之前会把绝对 `href` 归一成站内路径——验收的结构检查按控件语义（含 href）严格比较，绝对与相对链接指同一目标却会被判成缺陷（实测：像素 100% 的页面因这一条 failed）。

**证据绑定（2026-11-10）**：每次正式门禁先落一条 `incomplete` 记录，完成后更新同一条；超时、异常、中断和损坏都不能沿用旧的通过结果。最新记录按开始顺序及项目目录选择，验收任务与报告均完成后才可判通过。门禁前后和交付副本使用相同的文件筛选与 SHA-256 指纹；文件变化、旧报告没有指纹或读取失败时须重新验证。活动页同样按项目读取；没有项目归属的旧活动记录不再展示为当前项目结果。

指纹只覆盖本次会复制的项目文件，不覆盖依赖、构建产物、被排除的秘密文件、参考镜像或外部服务；也不能证明开发服务器实际运行的就是这些源码。前后指纹相同不能排除中途改动后又还原。运行期间应停止其他程序修改项目，并确认目标服务和参考镜像正确。

**正式基线怎么供给**（S4【实测】）：

- **不走引擎 `/static/`**。设了 `HEIMDALL_TOKEN` 时，验收 worker 在隔离的浏览器上下文里不带令牌，拿到 401，导航检查 `blocked / baseline_failed`。把令牌拼进 URL（`?token=`）能过，但只对路由 `/` 有效，而且令牌会原样写进 `report.json`。
- **不走 `clone-preview-server`**。它给 HTML 加的 `Content-Security-Policy: sandbox` 不含 `allow-same-origin`：镜像页访问 `navigator.serviceWorker` 抛错，Web 字体按跨源被拦，读 `cssRules` 也被拒。验收要求两侧都健康才判视觉，于是镜像对它自己的拷贝也是 `blocked / baseline_failed`。
- **做法**：`Gate` 封装每次运行起一个本机回环、随机端口、无令牌、不加 sandbox 的只读静态服务来供基线，运行结束即关。这个源上没有任何别的接口，放开 same-origin 的风险可控。
- **镜像先体检**。apify.com/contact 的镜像仍残留第三方嵌入（doubleclick），还有本地 404，所以换了供给方式基线依然不健康。提交前先跑健康探针；不健康时生成「正式基线副本」，去掉外部请求、移除断链引用，改动写进证据。仍不健康的，该维度记 `blocked` 并写明原因，而不是 `failed`。
- **实现（2026-10-26）**：`core/src/agent/gate/baseline.mjs` + `heimdall gate baseline <siteId> <page>`，报告写 `workspace/<siteId>/agent/gate/<page>/baseline.json`（`healthy` / `sanitized` / `blocked`，逐条改动与证据 SHA-256）。本机 8 页实测：6 页直接健康；thordata.com/home 只摘 3 个第三方 iframe（Google 登录、LiveChat、Cookiebot），页高 8861px 不变；apify.com/contact 摘 3 个 doubleclick iframe、替换 10 个外部图片与 2 个断链资产，页高 3389px 不变；stripe.com/home 2 处改动后健康；0 页 `blocked`。

快速裁判与正式裁判的偏差（【A-11】）。S4 在三个视口都在预算内的 apify.com/contact 上实测：

| 条件 | 三视口偏差 |
| --- | --- |
| 同一像素规则、同一拍摄流程（不做滚动预热） | 0.004–0.047 个百分点 |
| 快速裁判改用 `diff.mjs` 规则 | 1.1–2.4 个百分点 |
| 快速裁判多一次滚动预热 | 375 下 1.3 个百分点（预热让页高 +96px，3% 像素不同） |

所以快速裁判必须与验收拍摄流程一致：不做滚动预热，像素规则相同。视觉维度改由评估器给出、与快速裁判共用代码之后，A-11 衡量的是「验收首屏视觉分 vs 评估器」这一交叉核对。评估器用灰度文字、验收用默认文字渲染，这一层差值 Ph2 再量，**以评估器为准**。

## 2. 证据准备：简报与分段

### 2.1 简报由什么组成

目标：中位页 `outline` 级简报 ≤ 1.5 万 token（【假设 A-2】）。下表的体量是原型实测或估算，不是承诺。

| 部分 | 内容 | 体量 | 来源 |
| --- | --- | --- | --- |
| 大纲 | 标签、`id`、前两个类名、`role`、少量属性、直接文本前 60 字符；折叠重复兄弟；深度 ≤ 14 | 2–15 千 token【实测原型，[01 §1.4](01-background.md)】 | `dom.html` |
| 分段表 | 每段：ID、角色、三视口边界框、锚点、依赖、体量估计 | 1–2 千【估算】 | 分段算法（§2.2） |
| 设计令牌 | 颜色 / 字体 / 字号 / 间距 / 圆角 / 阴影 / 断点，按使用频次取前 N | 1–3 千【估算】 | `extractTokens` |
| 资产索引 | 编号、类型、尺寸、字节数、被哪些段引用 | 1–3 千【估算】 | `asset-map.json`、CAS |
| 字体清单 | 家族、字重、本地文件 | < 1 千 | 捕获的字体 |
| 交互与动效 | 可交互控件、`motion.json` 摘要 | 0.5–2 千【估算】 | DOM + `motion.json` |
| 接口摘要 | 方法 + 路径模板 + 状态 + MIME + 次数（无正文） | 0.5–2 千【估算】 | 清洗后 HAR |
| 缺口与历史 | 已知缺口、门禁历史 | < 1 千 | `clone-gaps.json`、账本 |

所有来自网页的字符串都在围栏内（E6-15，[08 §3](08-security-governance.md)）。

### 2.2 分段算法

分段（SectionPlan）是并行构建、局部修复和局部对比的基础，所以要**稳定**（同一页多次生成 ID 不变）。

1. **候选容器**：`body` 与 `main` 的直接子块、`header / nav / section / footer / aside`、带 landmark `role` 的块、高度 ≥ 48px 的块级元素。
2. **叠放层单列**：`position: fixed / sticky` 的元素（吸顶导航、悬浮按钮、cookie 条）不参与纵向切分，作为 `overlay` 段单独列出，避免与正文段重叠。
3. **纵向切分与合并**：按几何分隔（背景色或边框变化、大间距）合并过碎的块、拆开过长的块。1440 宽下目标段高 300–1200px【假设】，375 宽下按同一 DOM 锚点重新量取边界框。
4. **稳定 ID**：`sec-<role>-<hash(锚点路径 + 前 20 个字符)>`。
5. **每段产出**：三视口边界框、DOM 锚点（CSS 路径 + 文本锚点）、参考裁剪图、子树大纲、命中的 CSS 规则、资产引用、依赖。
6. **共享组件候选**：跨页的标签结构哈希 + 文本模糊匹配相似度 ≥ 0.9 的段（页头、页脚、导航）进入 `sharedCandidates`，整站重建时先建先复用。
7. **覆盖检查**：覆盖页面高度 ≥ 98%，重叠 ≤ 2%，否则调整或标 `needs_review`。

特殊情况：横向滚动区、全屏背景视频段、无限滚动（只取前 N 屏并标注）、超过 12,000px 的页面（分块，成本上升）。

### 2.3 渐进披露的五层

| 层 | 工具 | 返回 | 典型体量 |
| --- | --- | --- | --- |
| L0 | `overview` | 站点列表、页面状态、能力与预算 | < 1 千 token |
| L1 | `brief(detail: outline)` | 页面简报（§2.1） | 1–2 万 |
| L2 | `brief(detail: sections)` | 分段表 + 每段摘要 | 2–4 万 |
| L3 | `brief(sectionId, detail: full)` | 该段子树大纲 + 命中规则 + 样式摘要 + 资产 | ≤ 2.5 万（默认上限） |
| L4 | `artifact(uri)` | 原始文件的范围读取（最后手段） | 按需，受预算截断 |

每层都返回「如何取下一层」。模型默认停在 L1–L3，几乎不需要碰 L4。

### 2.4 每段的样式摘要

这是让模型「不猜」的关键，也是 `faithful` 档能快速逼近 Gold 的原因。

- **命中规则**：从 CSSOM 取出选择器命中该段任一元素的规则（含 `@media`、`@supports`），去重、按来源顺序保留。`faithful` 档原样给出，可以直接作用域化后复用。
- **计算样式签名**：对段内元素按 ~25 个属性求签名并分组，输出「签名表 + 元素引用签名」，比逐元素展开压缩 5–10 倍【估算】。
- **令牌引用**：值命中前 N 个令牌时用令牌名代替字面值。

## 3. 对比与修复包

### 3.1 快速对比流水线（E6-09、E6-10）

1. **取候选**：URL（dev server），或项目目录（读 `heimdall.config.json` 的 `devServer`；启停由调用方负责）。
2. **同条件渲染**：Chromium、同样的视口、**同样的冻结策略**（沿用 `freeze.mjs`：CSS 动画全冻、轮播回初始位、输入框清空）、同样的等待（网络安静上限 + 字体就绪 + 静置毫秒）。两侧必须同条件，否则差异里全是环境噪声。**Ph0 补充**：
   - 不做滚动预热，与验收 runner 一致（S4：预热会让部分页面变高）。
   - 文字用灰度抗锯齿（`--disable-lcd-text`）。S1：Windows 上默认是 LCD 亚像素抗锯齿，0.5px 的错位就会改变彩色边缘，噪声误报因此高 2–4 倍。
   - 页内程序化滚动要显式 `behavior: 'instant'`。thordata.com 设了 `scroll-behavior: smooth`，普通 `scrollTo` 是异步动画。
   - 判断元素可见时，只对目标元素临时打开 `pointer-events`。不少站给图片设了 `pointer-events: none`；apify.com 还有一层 `pointer-events: none` 的全屏透明层，全局打开会挡住一切。
3. **截图**：每视口整页；超过 12,000px 分块。
4. **行对齐**（Ph0 新增，S1 验证）：上方一个块高度变了，下方整页都会错位；不对齐的话，差异图从那一行往下全红，修复包只能说「下面全错了」。对齐的做法：
   1. **锚点与递归**：以逐行哈希做 patience diff，即用两侧都只出现一次的行做锚点，递归处理锚点之间的区间，再剥掉共同前后缀。锚点必须前后至少连着 3 行在同一偏移上相等，或者与区间两端的偏移一致。截图里两行像素碰巧一样并不罕见，只靠孤立一行会造成「删 12 行再插 12 行」的假对齐。
   2. **高度变了的段保留两种映射**（顶对齐、底对齐）：两种映射下都对不上的像素才算差异；只在底对齐下对得上的，是「被推开的内容」，单独报（内容没变，只是位置移了 Δ）。这样多栏布局里只有一栏被推开的情况也能说清。
   3. **接缝规则**：±1 行纯色空白的伸缩不报；「插 k 行……删 k 行」成对出现时，还原成中间那段内容的整体 `shift`（dy = ±k）。

   `heightDelta` 照常记录。门禁用的像素分**不受对齐影响**，仍按 §1.2 直接逐像素比。
5. **像素差 → 区域**：应用遮罩 → 差异图 → **±1px 容差**（某个像素的值落在对侧 3×3 邻域的取值范围内，且对侧亦然，就算抗锯齿差别）→ 4px 格子膨胀 3 格后取连通块 → 区域。紧挨着、且都落在同一个紧凑参考元素里的区域合并成一个（元素面积 ≤ 两区域外接框的 4 倍）。S1：一张留白多的插图被藏掉，差异会碎成 2–3 块。容差只用来找区域和排序，不改门禁分。
6. **区域 → 分段**：按边界框与参考侧分段的重叠归属。
7. **原因分类（v1 启发式）**：

| cause | 判据（启发式，输出置信度） |
| --- | --- |
| `shift` | 把候选裁剪图平移 (dx, dy) 后差异下降 ≥ 60%（沿用 `diff-shift` 的思路），并给出 dx、dy |
| `missing-content` | 候选区域接近纯背景（边缘密度低），参考区域有内容 |
| `image-missing` | 参考区域是图像（色彩方差大、无文字形态），候选是平色或占位 |
| `size` | 同一分段的高度或块尺寸与参考不一致，差异沿边缘分布 |
| `color` | 边缘图高度相关，但颜色均值偏移超过阈值 |
| `font` | 文字形态区域，行宽 / 字形差异，但布局对齐 |
| `spacing` | 投影轮廓平移，行 / 块间距变化 |
| `overflow` | `scrollWidth > clientWidth` |
| `behavior` | 来自行为环的回放差异 |
| `unknown` | 以上均不满足 |

   Ph0 补充两个原因：`extra-content`（候选多出参考里没有的内容；多出的是一整块单色时按 `color` 报，多半是背景色变了）；被推开的内容按 `spacing` 报并给 `shift: {dx: 0, dy: Δ}`。S1 实测原因判对率约 77%（命中区域中）：缺图 94–100%、缺块 88–94%、字号 65–83%、颜色 65–72%、平移 61–67%，间距类插入点在空白里位置不唯一。所以 v1 的 `hint` 必须带置信度，模型要以裁剪图为准；原因的精度靠 v2（§3.2–3.3）。

8. **生成修复包**：每视口的区域按「面积 × 严重度」排序，再做两步修正。
   - **参考计算样式（2026-10-27 增补）**：每个区域除「参考元素 ref」外，还带该元素的参考计算样式（`display / width / height / padding / margin / gap / fontSize / lineHeight / fontWeight / letterSpacing / color / backgroundColor / borderRadius / border` 等，只留非默认值），`packet.txt` 里逐条打印成「参考样式: …」。理由是 Bench 实测：只给「字号不对」时同一模型只能到 60–68 分，给出精确数值的分段证据后到 94–98 分——**没有数字的提示等于没提示**。
   - **候选计算样式与样式差（2026-10-30 增补）**：同一条目还带候选元素自己的 `cand.style` 与 `styleDiff`（`prop / ref / cand / delta`），`packet.txt` 打印「候选样式 / 样式差」，例如 `fontSize 参考 52px / 候选 46px（−6）`；`element.diffs` 补扫区域内其他有样式差的子元素（字号、颜色常落在更小的元素上）。这解决的是「参考值已知、候选值未知」的最后一公里：375/768 的 3px 换行差不再靠猜。
   - **级联修正**：从上往下，下方随高度变化被推开或跟着变高的区域，权重压到上方「根」的 0.9 倍以下，并标 `consequenceOf`。S1：字号 +2 的段落引起的连带区域面积远大于它本身，按面积排它会掉到第 12 位。
   - **集中度修正**：差异像素占外接框不足 10% 的区域按比例降权（最低 0.2 倍），不足 5% 的标为「零散」，严重度为 low。真缺陷的差异成片，S1 约 20–40%；容差之后残留的渲染噪声稀疏地散在整段文字上，约 2%。

   修正后取前 K 个（默认 12），每个区域带参考 / 候选 / 差异三张裁剪图（四周加 24px 余量，默认长边 ≤ 1568 以省 token，需要看清细字时可要 2576）。一个修复包的图片数默认 ≤ 12 张。S1 原型把三张拼成一张（宽区域上下拼，高区域左右拼），一个区域只占一张图。
9. **趋势**：与同候选上一次运行比较，给出 `better / same / worse / oscillating / stagnant`。
10. **判定状态**（快速裁判，**没有 `passed`**）：`fail`（任一视口低于 bronze 阈值，与[附录 C §6](appendix-c-schemas.md) 一致）、`needs-work`（未达目标等级）、`near`（距目标等级阈值 ≤ 1 个百分点且无 `high` 区域，【假设】待校准）、`pass-candidate`（所有视口达到目标等级的像素、最大块与最大集中区域阈值、无 `high` 区域，但尚未经正式裁判）。

v1 只给「哪里、什么原因、多大、怎么对」；v2（§3.2–3.3）再加「是哪个元素、哪个属性差多少」。

### 3.2 元素对应（E6-11）

`style-probe` 当年按 DOM 路径配对，是因为镜像与原站 DOM 一致。**重建后的 DOM 不同**，必须换成与结构无关的对应。

- **特征**：段内归一化边界框、规范化文本（前 80 字符）、角色 / 标签、图像感知哈希（`<img>` 与背景图）、层级深度、兄弟序。
- **代价**：`cost = w1·(1−IoU) + w2·文本距离 + w3·角色不符 + w4·图像哈希距离 + w5·位置偏移`。
- **匹配**：段内用匈牙利算法求最小代价指派；`confidence = 1 − 归一化代价`：≥ 0.8 为匹配，0.5–0.8 为弱匹配，< 0.5 视为未匹配。
- **重复内容**（卡片列表、重复按钮）：用顺序约束（最长公共子序列）辅助，避免错配。
- **输出**：匹配对 + 两侧未匹配列表（未匹配的参考元素计入 `structure` 缺失）。
- **回退**：置信度低时只给区域，不给元素，不让模型被错误线索误导。

### 3.3 属性差（E6-16）

对置信度 ≥ 0.8 的匹配对，比较 `fontSize / fontWeight / lineHeight / letterSpacing / color / backgroundColor / borderRadius / borderColor / padding* / margin* / width / height / display / textAlign / gap` 等（以 `style-probe.mjs` 现有 20 个属性为起点）。输出前几项差值，并归入 `color / font / spacing / size`。

### 3.4 模型看到的修复包

文本视图（同时附三张裁剪图）。下面是示意：

```
[r1440-03] 1440 · sec-hero-a41c07 · bbox(0,96,1440,540) · 面积 1.9% · high · cause=spacing
     元素: 候选 `main > section.hero > h1`  ↔  参考 `h1.hero-title`  （置信度 0.93）
     属性: marginBottom 24px→16px · lineHeight 1.2→1.1 · fontSize 56px→52px
     裁剪: ref=heimdall://run/run_20261104T031200Z_9f2a1c/crop/r1440-03/ref.png  cand=…/cand.png  diff=…/diff.png
     建议: 先改 fontSize / lineHeight，再看 margin
趋势: better（+1.4 pp，上次 run_20261104T030500Z_8e1b40）  ·  判定: needs-work  ·  下一步: 修 r1440-03、r1440-05，然后重新 compare
```

### 3.5 为什么这个循环会收敛

每次迭代，修复包把误差**局部化**到（区域、属性）并排好序；修复限定在一个分段内，不应影响其他分段；「变差即回退」让分数在被接受的状态序列上单调不降。这是局部爬山，**不保证全局最优**，所以停滞时有升级阶梯（§5.2），最坏的结果由 Floor=Mirror 兜住。A-1、A-5、A-10 就是在检验这个论证在真实模型上成不成立。

### 3.6 正式裁判接入

验收 Mirror 的输入是「基线入口 URL + 目标入口 URL + 相对路由」，路由 `/` 表示入口本身。每个页面单独跑一次：

```json
{
  "schemaVersion": 1,
  "name": "rebuild-thordata.com-home",
  "mode": "mirror",
  "baselineUrl": "http://127.0.0.1:51734/thordata.com/home/index.html",
  "targetUrl": "http://127.0.0.1:5199/",
  "routes": ["/"],
  "thresholds": { "visual": 0.97 },
  "normalization": { "maskSelectors": [] }
}
```

（示意）。Ph0 核对的四件事与结论（S4，【实测】，直接调用 `runner.mjs` 的 `runAcceptance()`，证据写在 spike 目录，不进真实验收存储）：

| # | 待核对 | 结论 |
| --- | --- | --- |
| ① | 基线 URL 的 origin / 路径形态能否被接受 | **能**：本机回环 HTTP、文件形式（`…/clone/index.html`）与目录形式（`…/clone/`）都通过计划校验；唯一的限制是基线与目标不能相同。但「能接受」不等于「能判」：供给方式决定基线是否健康，见 §1.5 |
| ② | 设了引擎令牌时 worker 访问 `/static/` | **会 401**：隔离上下文不带令牌，导航检查 `blocked / baseline_failed`。拼 `?token=` 只对路由 `/` 有效，且令牌写进 `report.json`。结论：基线不走引擎，由 `Gate` 封装起临时回环服务（§1.5） |
| ③ | 限额对「每页一次」够不够 | 8 路由 / 3 视口 / 24 点 / 单次 5 分钟**够**：一页三视口一次 6–9 秒，18 项检查；同引擎串行（并发 409）。**卡住的是另外两条**：截图预算 12,000px / 1,200 万像素（thordata.com 首页三视口全超，只拍首屏），以及「两侧都健康才判视觉」（镜像残留的第三方请求、本地 404、sandbox 下的脚本错误都会让基线不健康）。两条都在指纹冻结文件里，由评估器与基线体检绕开（§1.5） |
| ④ | 多视口克隆的视口选择器 `index.html` | **能自动落到对应变体**：选择器在 DOMContentLoaded 前就跳到 `index-375 / 768 / 1440.html`，验收三视口截到的文档高度与各变体一致（apify.com/contact 实测）。基线直接用 `clone/index.html` 即可 |

## 4. 保真旋钮与技术栈配置

### 4.1 保真旋钮（E7-05）

同一个站，用户其实有三种想要：「尽快、尽量像」「像且好维护」「干净的设计系统」。旋钮把这个选择显式化，它同时改变**简报给什么、技能怎么指导、默认门禁、迭代预算**。

| | **faithful** | **balanced（默认）** | **idiomatic** |
| --- | --- | --- | --- |
| CSS 来源 | 复用捕获的 CSS 规则，按分段作用域化（CSS Modules 或带分段前缀的类） | 令牌 + 工具类（Tailwind）为主，复杂片段保留原规则 | 全部改写为设计系统，不留冗余规则 |
| DOM | 贴近原站结构 | 按分段组件化，保留语义 | 语义组件，结构可与原站不同 |
| 简报给什么 | 命中规则原文 + 令牌 | 令牌 + 签名样式表，必要时给规则片段 | 令牌 + 设计意图摘要，规则不给全文 |
| 默认门禁 | gold | silver | silver |
| 迭代 / 成本 | 少、便宜 | 中 | 多、贵 |
| 适合 | 迁移基线、回归对照、「先要一个能用的」 | 大多数重建 | 要长期维护的新代码库 |

A-9 检验：`faithful` 的 Gold 达成率是否显著高于 `idiomatic`，否则旋钮没有意义，需要合并档位。

### 4.2 技术栈配置（Stack Profile）

一个配置 = 一套**锁版本的脚手架** + 约定 + 命令，由 `rebuild init --stack` 展开。

| 内容 | 说明 |
| --- | --- |
| 脚手架 | 模板目录，依赖版本锁死；包源可配（国内可用镜像） |
| 目录约定 | 页面、组件、令牌、资产放哪；添加页面 / 路由的方法 |
| 命令 | 安装、`dev`（端口可配）、构建、检查 |
| 资产约定 | 一律引用 `/assets/<hash>.<ext>`；字体通过生成的 `@font-face` 引用本地文件 |
| `AGENTS.md` 片段 | 该技术栈的写法要求与禁忌 |
| 门禁入口 | `devServer.url`、各页面路由 |

| 配置 | 阶段 | 说明 |
| --- | --- | --- |
| `html-css` | Ph1 | 语义 HTML + CSS 变量（`tokens.css`）；最快到 Gold，适合静态站和基线 |
| `vite-react-ts-tailwind` | Ph1 | 主推 |
| `vite-vue3-ts-tailwind` | Ph3 | 本仓库控制台用 Vue 3，团队熟悉；国内使用面广 |
| `nextjs-app-router`、`astro` | Ph4 | 赛后 |

### 4.3 资产与字体

资产来自内容寻址存储（CAS）里的**原件**，落到 `public/assets/<hash>.<ext>`，并生成 `assets.json`（原始 URL、用途、被哪些段引用）。禁止外链、禁止「照图重画」（门禁的 `assets` 维度检查）。默认不做有损压缩。字体用捕获到的字体文件生成 `@font-face`。

### 4.4 响应式

断点取自 CSSOM 的 `@media`（令牌中已有），三视口边界框告诉模型每段在 375 / 768 / 1440 下的形态。技能要求按原站断点实现，不自创断点。

## 5. 收敛控制

### 5.1 单段循环

```
for 段 in 计划顺序:                       # 叠放层 / 共享组件 → 自上而下
    最佳 = 无
    for i in 1..段迭代上限:               # 默认 4
        候选 = 代理.写(段, 简报(段), 上次修复包)
        r = compare(候选, 范围=段, mode=fast)
        if r 优于 最佳: 最佳 = r; 提交(); else: 回退()
        if r.判定 == pass-candidate: break
        if 停滞(r.趋势) 或 振荡(r.趋势): 升级(段)
整页 = compare(候选, 范围=页, mode=fast)    # 抓段间干扰：外边距折叠、吸顶遮挡
门禁 = compare(候选, 范围=页, mode=formal)  # 唯一能宣布 passed 的一步
```

### 5.2 停滞升级阶梯

| 步 | 动作 |
| --- | --- |
| ① | 该段切到 `faithful`：简报给命中规则原文，直接复用 |
| ② | 拆成子分段，各自循环 |
| ③ | 请求人类提示（控制台「AI 活动」弹出，或代理向用户提问） |
| ④ | 接受残差，写入残差清单，继续下一段 |

### 5.3 顺序

叠放层与共享组件先行 → 页面自上而下 → 整页对比 → 正式裁判。整站：共享组件只建一次；逐页循环；最后做全站复验（对重建项目运行 `verify --all --resume` 等价流程，E7-13）。

### 5.4 回退

`rebuild init` 把工作区初始化为 git 仓库。技能要求**每次迭代提交**；`compare` 返回 `trend: worse` 时建议回退；赛后 Autopilot 自动回退。

### 5.5 终态与交付

| 终态 | 交付物 |
| --- | --- |
| `passed` | 重建项目 + 门禁报告 + 镜像附件 |
| `passed_with_residuals` | 同上 + 残差清单（接受的偏差及原因） |
| `failed_with_residuals` / `budget_exhausted` / `cancelled` | **镜像 + 报告 + 残差清单**（Floor=Mirror），重建项目作为「未通过的草稿」附上并明确标注 |

**实现（2026-10-26，E7-10）**：`heimdall rebuild deliver [--project .] [--out D]`。交付包 = `mirror/`（冻结镜像，双击即可看）+ `project/`（源码，不含依赖与构建产物；非 `passed` 时带 `DRAFT.md`）+ `REPORT.md` + `residuals.json` + `delivery.json` + `MANIFEST.jsonl`（逐文件 SHA-256）。终态只取上表五种；`passed` 只认正式裁判（E7-07），没有正式结果时按 `failed_with_residuals` 交付并把原因写成 `formal_gate_missing`——**不假装通过**。正式裁判上线后，交付会自动读取**同一项目目录**最近一次 `gate formal` 的结果（`agent/gate/<page>/formal-*.json`），别人的工作区或早期没有 `projectDir` 的报告一律不认。

**2026-11-10 补充**：未完成仍沿用固定交付终态 `failed_with_residuals`，但原因明确为 `formal_gate_incomplete`，不表示已证实产品失败。源码和镜像复制时排除已识别的 `.env`、密钥、证书和登录态路径；这是路径过滤，不保证文件正文、截图或其他文件不含秘密，分享前仍须人工检查。自定义输出目录必须为空，且不能放在项目目录内；历史交付包不会自动清洗或改写。

正式基线服务和新生成的基线副本也排除这些秘密路径及符号链接。它仍是本机服务，不是对抗本机恶意程序的安全隔离；检查和读取之间的并发替换不在保证范围。每次正式门禁生成独立基线副本，历史副本保留，长期使用应关注磁盘占用。

## 6. 模型用法与成本

### 6.1 谁干什么

| 任务 | 推荐模型 | effort | 说明 |
| --- | --- | --- | --- |
| Gold 档分段首版、复杂布局 | Opus 5.5 | `high` / `xhigh` | Opus 5.5 默认 effort 是 `medium`，**写代码类任务要显式调高** |
| 默认档分段首版与修复 | Sonnet 5.5 | `high` | 性价比主力 |
| 简单段 / 重复段 / 机械改动 | Sonnet 5.5 或 Haiku 5.5 | `medium` | 省钱 |
| 分类、摘要、命名、批量标注 | Haiku 5.5 | `low` | — |
| 反复卡住的收敛 | Fable 5.1（按需升级） | `high` | 价格最高，只在升级阶梯里用 |

外部代理模式（E0）下，模型由用户的客户端决定；技能按能力分档（E4-06）。

### 6.2 上下文与缓存

一次迭代的上下文 = **稳定前缀**（技能 + 该段简报 + 令牌）+ **可变部分**（上次修复包 + 裁剪图）。稳定内容放前面、可变内容放后面，才能吃到提示缓存（Opus 5.5 缓存读 $0.20 / 百万 token，约为输入价的 1/20）。1M 上下文装得下一页的多轮迭代（A-8 检验是否真的不需要压缩）。

### 6.3 视觉 token

高分辨率图片长边最多 2576px，按上限计约 4.8 千 token / 张（Sonnet 5 文档口径，Opus 量级相近）【调研·估算】。所以修复包默认把裁剪图缩到长边 ≤ 1568，需要看清细字时才升到 2576；一个修复包默认 ≤ 12 张图。

### 6.4 成本估算【估算】

公式：`成本 = 分段数 × 每段迭代数 × (稳定前缀写缓存 + 可变输入 + 输出)`，再加整页对比与正式裁判的开销。

| 假设 | 值 |
| --- | --- |
| 分段数 / 页 | 8 |
| 每段迭代数 | 3（首版 + 2 次修复） |
| 每次迭代输入 | 约 2 万 token：稳定前缀 1.2 万（首次写缓存，之后读缓存）+ 可变 0.8 万（含 2 张图） |
| 每次迭代输出 | 约 4 千 token |
| 调用数 | 24 |

| 方案 | 估算 / 页 | 备注 |
| --- | --- | --- |
| Opus 5.5，balanced | 约 3.5–4.5 美元 | 输出约占一半；缓存写读约 0.5 美元 |
| Sonnet 5.5，balanced（默认档） | 约 1.7–2.3 美元 | 约为 Opus 的一半 |
| Sonnet 5.5，faithful | 约 1–1.5 美元 | 迭代更少 |
| 10 页站，共享组件复用后约 6 个等效页 | Sonnet 约 10–14 美元；Opus 约 21–27 美元 | 共享组件只建一次 |

**Phase 0–3 的总花费上限（README D-2）约 300 美元**。分解见 [09 §2.3](09-quality-metrics.md)：spike 与 Bench（S0–S3）约 200 美元，开发迭代与彩排约 70 美元，赛前余量留给行为 / 契约评测（S4，约 30 美元以内）。

**Ph0 实测（S2【实测】，thordata.com 首页两个分段）**：

| 项 | 实测 |
| --- | --- |
| 样本 | 两个分段：图文两栏 + 手风琴，1320×770；产品卡片网格，1320×863 |
| 简报 | 本节的 balanced 形态：每个元素三视口外接框 + 计算样式签名，不给 CSS 规则原文 |
| 栈与拍摄 | `html-css`；Web 字体正常加载 |
| 质量 | Claude Opus 5.5 跑 4 次（每段 2 次），**4 次都在第 1 次快速对比就到 gold**，三视口 99.55–100%。DeepSeek-v4.1-flash 跑 1 次，第 2 次到 gold（8.6 分钟）。GLM-5.3-flash 跑 1 次，第 3 次到 silver（98.3–98.9%，49 分钟、116 次工具调用） |
| 每段花费 | Opus 5.5 为 **1.55–3.13 美元**（按 §6.2 价目，用运行记录里的 token 数折算）。输出 3.9–9.5 万 token（含思考）、写缓存 9–14 万、读缓存 100–232 万，读缓存占输入 90–94% |
| 每段用时 | 10.6–24.4 分钟，20–32 次工具调用 |

**比上表的估算贵 3–6 倍，而且贵不在迭代上**：每段只跑了 1 次对比。钱和时间花在模型自己量参考图上：四次运行都先写脚本解码 PNG，量亚像素偏移、细线颜色、伪元素画出的线、写死的高度。这些都是简报没给的事实（[04 E6-04](04-requirements.md)），也是 [04 E6-17](04-requirements.md) 度量工具要省掉的部分。

按每页 8–12 段外推，Opus 5.5 一页约 **15–30 美元**、串行数小时（可并行）。**G4 的 Gold 档 ≤ 6 美元 / 页按现在的做法达不到**。Ph2 Bench v0 用三个手段复测：简报补齐五类事实（E6-04）、度量工具（E6-17）、同一会话连做多段以摊薄上下文。仍不达的话，按 [09 §2.6](09-quality-metrics.md) H7 修订目标并留痕。DeepSeek 一段 8.6 分钟到 gold，提示经济档可以用更便宜的模型，但本机网关没有回报它的 token 数，成本待 Bench 用直连 API 测。

**目标（G4）据此设定**：默认档（Sonnet 5.5，balanced）中位页 ≤ 3 美元、≤ 15 分钟；Gold 档（Opus 5.5）中位页 ≤ 6 美元（【假设 A-1】）。Ph0 状态：Gold 档实测未达（见上）；Sonnet 5.5 在本机无法派发，未测（[10 §4](10-roadmap-risks.md) R17）。

### 6.5 工具定义本身的成本

核心 8 个工具的定义约占 3 千 token 上下文（当前 17 个约 6.7 千）【估算】；技能列表项约 1.5 千字符。支持工具搜索（延迟加载）的客户端可以进一步降低。这也是 [02 §6.4](02-strategy.md) 把工具数压到最少的原因。

### 6.6 弱模型

`economy` 档技能：分段更小（≤ 600px）；每次迭代只改一类属性；给出显式检查清单；更多使用 `faithful` 档的规则复用。国产模型是否可达 Silver 由 Bench 回答（E10-03 / E14），不预设结论。

### 6.7 拒绝与降级

重建、尤其后端契约环的措辞（抓包、接口分析）有被安全分类器误判的可能。Autopilot 必须处理 `refusal` 并启用服务端降级（E10-05）；外部代理由客户端处理，技能里写明遇拒绝时的退路（换措辞说明用途、改走 `faithful`、请用户确认授权范围）。

## 7. 做不到的事与上限

诚实地列出来，并规定如何**报告**——沿用项目「缺口可枚举」的做法。

| 类型 | 现象 | 怎么处理 / 报告 |
| --- | --- | --- |
| WebGL、Three.js、运行时 `<canvas>` | 捕获的是光栅化的一帧，没有运行时 | 静态化为图片资产；`gaps` 标 `runtime-drawn`；行为维度不覆盖 |
| 视频、音频 | 只有封面 | 报告「无播放」；不计入视觉缺口 |
| 滚动编排（固定场景、视差、滚动驱动动画） | 只保留结束态 | `motion.json` 列出；残差清单 |
| 第三方嵌入（地图、视频平台、广告、客服挂件） | 离线时是空的 | 占位；断网门禁要求零外联，故必须占位并报告 |
| 动态内容（时间、随机、A/B、个性化） | 每次渲染不同 | 遮罩 + 冻结参考；参考不稳定则 `needs_review` |
| 登录后页面 | 需要人工保存的会话 | 沿用「人工登录一次、机器复用」；参考包按秘密处理；不外发 |
| 无限滚动、虚拟列表 | 只能取到前 N 屏 | 报告覆盖范围 |
| 超长页面（> 12,000px） | 分块比对，成本上升 | 提示用户分段范围 |
| 反爬、WAF 拦截 | 捕获失败，没有参考 | 如实报告，不规避 |
| Shadow DOM、跨域 iframe | 能否完整还原取决于捕获 | `gaps` 标注 |
| 暗色模式、打印样式、多语言路由 | 默认不在门禁内 | 用户声明才纳入，声明即进入配置 |

任何重建结论都只覆盖**声明的视口、声明的页面、声明的流程**，报告里写明，不使用「任意站点」「100% 还原」一类措辞。
