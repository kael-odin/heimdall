- 项目：Heimdall
- 命题：极客 AI 命题展示 PDF 第 02 题
- 方案版本：2026-10-16
- 当前定位：方案规划与后续路线；Mirror / Regression 已有可运行 MVP，具体支持范围见[实现指南](acceptance-workbench.md)，固定注入评测见[演示测试集](acceptance-demo.md)。下文 P2—P4 不代表已经完成。
- 推荐样例：Xspark 代理 IP 平台（已获授权的测试环境或脱敏样例）

## 一、先给结论

这道题最适合沿用 Heimdall 现有积累。Heimdall 已经具备真实浏览器采集、多视口截图、像素与 DOM 差异、交互回放、资源缺口分析、离线验收和证据报告。比赛 MVP 不需要先完成 Figma 接入，也不需要把“还原度”压缩成一个像素分数。

推荐采用三种验收模式，按比赛展示价值和实现风险排序：

| 模式 | 参照物 | 比赛定位 | 结论 |
| --- | --- | --- | --- |
| **Mirror** | 源网站或已批准版本 | MVP 主线 | 判断开发项目与可运行基线在视觉、结构和交互上的差异 |
| **Spec** | PRD、验收清单、OpenAPI、Figma 意图 | 后续增强 | 判断实现是否满足明确需求和接口契约 |
| **Regression** | 上一个已批准版本 | 持续验收 | 判断新提交是否引入回归，适合 CI 和发版门禁 |

“还原度”应拆成四个可解释维度：**结构一致性、视觉一致性、行为一致性、业务一致性**。总分只用于排序和概览，不能替代具体问题、复现步骤和证据。

Figma 的正确定位是**设计意图来源**，不是唯一真值，也不应直接把设计稿 PNG 与网页 PNG 做绝对像素相减。当前只有 View 权限也不会阻塞 Mirror MVP；拿到权限后，可把 Frame、节点尺寸、间距、颜色、字体和状态转换成带容差的验收点。

### 2.2 团队建议的产品承诺

比赛答辩时建议把承诺收敛为一句话：

> 给定一个有授权的基线和一个待验收项目，Heimdall 自动执行页面、接口和交互验收，定位可复现的差异，输出带截图、请求、DOM、响应和复现步骤的 BUG 证据包。

建议主动说明三件事：

1. 系统会把环境差异、动态数据和源站自身问题单独标记，不会把所有差异都定性为目标项目 BUG。
2. 没有可靠参照物时，系统只能输出“观察/待人工复核”，不能伪造确定结论。
3. AI 可以帮助归类、解释和生成候选用例，但最终结论必须能回到浏览器、接口、代码或数据库证据。

## 三、什么叫“还原度”

### 3.1 四个维度

| 维度 | 检查内容 | 典型证据 | 是否适合直接打分 |
| --- | --- | --- | --- |
| 结构 | 路由、页面数量、标题、DOM 层级、组件存在性、资源引用 | URL 清单、DOM 快照、资源清单 | 适合，需先确认页面身份没有碰撞 |
| 视觉 | 布局、尺寸、间距、颜色、字体、图片、响应式状态 | 多视口截图、差异图、元素几何信息 | 适合，需处理字体、动画和动态内容 |
| 行为 | 点击、展开、Tab、菜单、表单、跳转、ARIA 状态 | 操作回放、URL、DOM 状态、网络请求 | 适合，必须声明操作和断言 |
| 业务 | 状态机、字段、权限、错误码、数据变化、跨系统回调 | API 响应、DB 只读查询、网关日志、状态链路 | 适合，但需要明确契约和测试夹具 |

可采用如下概览公式，但公式本身不是官方指标：

```text
overview = 0.25 * structure
         + 0.30 * visual
         + 0.20 * behavior
         + 0.25 * business
```

任何一维没有参照物时，应输出 `unknown` 或 `needs_review`，不要用默认满分补齐。安全、权限、数据泄露和关键业务失败可以作为硬门禁，即使总分较高也必须阻断通过。

### 3.2 差异不等于 BUG

系统应先判断差异类型，再判断是否是 BUG：

| 差异类型 | 例子 | 默认结论 |
| --- | --- | --- |
| 目标缺陷 | 按钮不可点击、接口字段错误、移动端菜单丢失 | BUG |
| 环境差异 | 域名、测试数据、时区、价格、库存、JWT、第三方回调 | 环境差异或待复核 |
| 基线缺陷 | 源站自身错误、旧版本已知问题、设计稿与产品规则冲突 | 基线问题，不直接归责目标 |
| 不稳定差异 | 动画帧、广告、随机 ID、时间戳、异步排序 | 先归一化，无法归一化则待复核 |
| 无参照观察 | 发现异常但没有需求或批准基线支持 | 观察/待人工复核 |

问题卡必须携带 `oracle`、`evidenceLevel` 和 `verdict`，让评委可以看出系统是依据什么下结论的。

## 四、参照物设计：不依赖单一 Figma

### 4.1 推荐的多层 oracle

按实际可靠性和可执行性，推荐建立以下参照层：

1. **运行基线**：源网站、已批准版本或冻结的测试环境。适合页面外观、路由和交互对比。
2. **需求基线**：PRD、验收清单、产品规则。适合文案、状态、权限和业务行为。
3. **契约基线**：Swagger/OpenAPI、事件 schema、错误码表。适合接口路径、参数、字段和枚举。
4. **现实证据**：真实浏览器、API 响应、数据库只读查询、网关和回调日志。适合确认实际行为。
5. **设计意图**：Figma Frame、组件变量和设计规范。适合确认尺寸、颜色、间距、字体和状态。
6. **人工批准**：对无法自动化的产品判断给出明确批准记录，并记录批准人、时间和范围。

冲突时建议遵循“业务规则优先于截图，运行事实优先于猜测，批准记录优先于旧产物”的原则。例如，Figma 上仍有一个旧按钮，但当前 PRD 已明确移除，则不能只凭设计稿报告目标项目缺陷。

### 4.2 Mirror 模式的真实答案

用户提出的“源网站和克隆网站对比是否更实际”，答案是：**是，适合作为比赛 MVP，但要把源网站定义为已批准的运行基线，而不是天然正确的真值。**

推荐流程：

1. 对源站冻结一次采集，记录 URL、视口、浏览器版本、登录态摘要、时间窗口和环境变量。
2. 对目标项目用同一组路由、视口和操作执行采集。
3. 先做环境归一化，再做截图、DOM、资源、交互和接口差异比较。
4. 对源站与目标站都执行健康检查；源站已经失败的断言标为 `baseline_failed`。
5. 只有在基线通过或被人工批准的断言上，才把目标差异定性为 BUG。

### 4.3 没有参照物时怎么办

没有源站、PRD、接口契约或人工批准记录时，系统仍可做静态检查和异常检测，例如明显的 404、控制台异常、横向溢出、按钮无响应、接口 5xx、敏感信息泄露。但报告中应使用以下状态：

```text
verdict = observation
confidence = low | medium
needsHumanReview = true
```

这比用模型猜一个“还原度 93%”更可信，也更符合比赛要求的可解释证据。

## 五、三种验收模式

### 5.1 Mirror：源网站/批准版本对比（比赛 MVP）

输入：`baselineUrl`、`targetUrl`、路由清单、视口、登录态、归一化规则和操作流程。

输出：

- 页面级视觉分、DOM 分和结构缺口。
- 多视口差异图和差异区域摘要。
- 交互步骤、前后状态、URL 和网络请求差异。
- 资源缺口、控制台异常、404、超时和横向溢出。
- 目标项目 BUG 卡和可复现证据包。

适合演示的缺陷：删掉移动端菜单、改错按钮跳转、隐藏某个字段、改错接口错误码、让续费状态显示错误。

### 5.2 Spec：需求/契约/设计对照

输入：`acceptance-point` 清单、PRD、OpenAPI、Figma 导出元数据和环境适配器。

输出：按需求编号汇总的通过、失败、阻塞、跳过和待复核清单。每条断言都包含复现步骤和证据，不再依赖“整页看起来像不像”。

### 5.3 Regression：版本回归门禁

输入：上一版已批准的快照、接口响应样本、操作流程和差异白名单。

输出：提交前的回归报告、变更区域、影响页面、风险等级和 CI 门禁结果。可把关键页面、关键接口和关键状态设置为硬失败，其余差异进入人工复核队列。

## 六、用 Xspark 做真实验收样例

Xspark 适合作为命题样例，因为它同时有需求、接口契约和真实测试证据三层材料：

- 需求层：`F:\学习手册\Xspark\代理IP调研\Xspark接手测试\01-总纲\星火-PRD与实现统合-20261014.md`。
- 契约层：`03-接口底表\_spec_official.json`、`03-接口底表\_spec_admin.json` 和接口坑位记录。
- 现实层：浏览器截图、API 响应、数据库对账、巡检 JSON、覆盖清单和历史测试报告。

### 6.1 可展示的验收点

| 编号 | 类型 | 验收内容 | 目标项目 BUG 例子 | 证据 |
| --- | --- | --- | --- | --- |
| `XS-API-001` | 契约/鉴权 | 开放 API 的鉴权头按已验证口径使用 `ApiKey`，无效鉴权返回预期 401 | 代码只接受文档中的 `Token`，导致真实客户端全部失败 | 请求头、状态码、响应 JSON、OpenAPI 规则 |
| `XS-BIZ-002` | 业务/UI | 概览页“7 天内到期=0”时不应继续显示续费入口 | 零到期数据仍显示续费按钮，误导用户 | DB 只读结果、页面截图、DOM 文本 |
| `XS-DATA-003` | 数据 | 续费后 `expire_time` 应按当前时间加天数秒数计算 | 将 `604800` 直接当 Unix 时间戳写入，页面显示异常日期 | 写操作前后 API、DB 对账、页面状态 |
| `XS-FLOW-004` | 状态机 | 域名解封从提交、CRM/OA、状态字段到网关放行的状态链路完整，超时可见 | 只更新前端状态，网关仍拒绝访问 | 请求链、状态变化、网关探针、超时记录 |
| `XS-VIS-005` | 响应式 | 390x844 下汉堡菜单可见，点击后展开，`aria-expanded=true` 且无横向溢出 | CSS 断点错位，按钮在移动端不可见或菜单被裁切 | 三视口截图、DOM 属性、布局宽度 |

这些点应作为脱敏的比赛 fixture，不直接对线上账户执行写操作。涉及续费、解封、删除等写操作时，使用独立测试账号、精确白名单和可回滚数据。

### 6.2 Xspark 已有能力如何迁移

Xspark 的以下积累可以直接转成 Heimdall 的输入或适配器：

- `copy_checks.json`：机器可读的文案和关键字段断言。
- `fingerprint_check`、`report_diff`：基线指纹和报告变化检测。
- Playwright 页面与交互巡检：操作步骤、截图、请求和状态记录。
- 状态化 E2E：把“提交后等待回调再验收”表达成状态机。
- `coverage-ledger-20261016.json`：页面、接口、状态和证据覆盖清单。
- `passed / skipped / not_run / blocked / incomplete`：比简单的通过/失败更适合真实环境。
- 精确写操作白名单、独立清理和证据门禁：作为安全执行层的默认策略。

## 七、建议的数据结构：acceptance-point

验收点是 Mirror、Spec、Regression 的共同中间表示，后续可以由 PRD、OpenAPI、Figma 或人工配置生成。

```json
{
  "id": "XS-VIS-005",
  "title": "移动端汉堡菜单可见且可展开",
  "mode": "mirror",
  "subject": {
    "route": "/overview",
    "viewports": ["390x844", "768x1024", "1440x900"],
    "state": "authenticated-readonly"
  },
  "oracle": {
    "kind": "approved-runtime",
    "source": "xspark-baseline-20261016",
    "priority": 1
  },
  "steps": [
    { "action": "goto", "url": "/overview" },
    { "action": "assertVisible", "selector": "button[aria-label='菜单']" },
    { "action": "click", "selector": "button[aria-label='菜单']" }
  ],
  "assertions": [
    { "kind": "visual", "region": "header", "tolerance": { "pixelRatio": 0.03 } },
    { "kind": "dom", "selector": "button[aria-label='菜单']", "attribute": "aria-expanded", "equals": "true" },
    { "kind": "layout", "expression": "scrollWidth <= clientWidth" }
  ],
  "normalization": ["mask:timestamp", "mask:avatar", "ignore:font-antialiasing"],
  "severity": "high",
  "evidenceRequired": ["screenshot", "dom", "console", "network", "steps"]
}
```

实现时应校验：ID 唯一、路由可解析、操作选择器有超时、断言类型受白名单约束、写操作需要显式授权、证据路径不能越出任务目录。每条结果都应带 `status`、`verdict`、`confidence`、`evidenceLevel` 和 `reproduction`。

## 九、系统流程规划

```text
基线登记
  -> 路由/接口/操作/视口/状态清单
  -> 环境归一化与脱敏
  -> baseline 与 target 同步执行
  -> 结构 / 视觉 / 行为 / 业务比较
  -> 差异分类（目标缺陷、环境差异、基线问题、待复核）
  -> 证据完整性检查
  -> 问题卡、复现步骤、报告和可选 CI 门禁
```

证据等级建议固定为：

- `真实流程`：实际浏览器/API/DB/网关闭环已跑通。
- `离线复现`：使用固定 fixture 复现，逻辑可信但未代表真实环境。
- `源码确认`：由代码路径确认，尚未跑通用户流程。
- `观察/待复核`：发现异常但缺少足够 oracle 或环境证据。

系统报告中必须把这四类分开，避免演示时把离线 fixture 说成生产通用能力。

## 十、评测指标建议

### 10.1 与 PDF 方向一致的核心指标

| 指标 | 建议定义 | 目标用途 |
| --- | --- | --- |
| 检出率/召回率 | 已注入并确认的 BUG 中被系统正确定位的比例 | 证明能发现问题 |
| 误报率 | 被系统判定为 BUG、但经人工确认属于环境/基线差异的比例 | 证明不会泛化误报 |
| 耗时 | 从基线登记到报告生成的 P50/P95 | 证明研发可用 |

### 10.2 Heimdall 建议补充指标

- **证据完整率**：失败问题中同时具备位置、步骤、断言、截图或 DOM、请求/响应摘要的比例。
- **覆盖率**：已执行路由、视口、状态、接口和操作数 / 声明总数。
- **可复现率**：同一 fixture 在重复运行中得到相同结论的比例。
- **分类准确率**：目标 BUG、环境差异、基线问题和待复核四类的人工一致率。
- **门禁准确率**：关键问题是否阻断，非关键波动是否进入复核而不误阻断。

建议比赛报告给出一个固定测试集：已知视觉缺陷、已知交互缺陷、已知接口缺陷、已知业务状态缺陷、动态噪声、源站缺陷和环境差异各若干条，并公开每一条的真值和证据。

## 十一、分阶段实现计划

### P0：验收输入和证据骨架

- 定义 `acceptance-point` schema、结果状态和证据等级。
- 为 baseline/target 固定浏览器、视口、时区、语言、网络和登录态摘要。
- 增加任务级目录、manifest、脱敏和可恢复清理。
- 先用本地 fixture 验证差异分类，不连接真实写操作。

### P1：Mirror MVP

- 同步采集源站与目标站。
- 支持 375/768/1440 三视口、DOM、截图、资源和控制台检查。
- 支持按钮、菜单、Tab、折叠和导航回放。
- 输出问题位置、差异图、复现步骤、证据文件和汇总分。
- 将动态数据、字体抗锯齿、时间戳、随机 ID 和广告区域做归一化。

### P2：Xspark 适配器和业务验收

- 导入 PRD、OpenAPI、`copy_checks` 和覆盖清单。
- 增加 API 请求/响应断言、DB 只读查询和状态机等待。
- 用脱敏 fixture 注入 XS-API-001 至 XS-VIS-005。
- 生成“源码确认 / 离线复现 / 真实流程”分层报告。

### P3：Spec 与 Figma 增强

- Figma View 权限可用后，导出目标 Frame PNG/SVG 和节点元数据。
- 建立 Frame → 路由 → 视口 → 状态映射。
- 将节点信息转成带容差的验收点，而不是直接像素相减。
- 支持组件状态、文字长度、间距和响应式约束的检查。

### P4：Regression 与 CI

- 固化已批准版本和差异白名单。
- 对关键页面、接口和状态设置硬门禁。
- 通过 GitHub Actions 或本地命令输出机器可读结果。
- 失败时保留最小可复现包，避免把完整登录态和敏感响应上传到 CI。

## 十二、Figma 的具体使用方式

### 12.1 Figma 适合解决什么问题

- 设计意图没有运行基线时，提供组件、间距、颜色、字体、尺寸和状态来源。
- 运行基线与实现都在变化时，提供稳定的设计约束。
- 发现“功能能用但明显偏离设计”的局部问题。

### 12.2 不适合直接解决什么问题

- 不能证明接口是否正确、权限是否正确或数据状态是否正确。
- 不能直接代表真实字体加载、浏览器渲染、滚动行为和第三方组件。
- 不能把一张设计稿图片当成所有视口和所有状态的唯一真值。

### 12.3 拿到 View 权限后的最小接入

1. 让设计侧指定目标 Frame、页面路由、视口和状态，不要把整份文件作为无边界输入。
2. 导出节点元数据和目标图，记录文件版本、Frame ID 和导出时间。
3. 对设计稿做字体、图标、动态数据和跨平台渲染归一化。
4. 把元数据转换成 `visual`、`layout`、`text`、`state` 四类验收点。
5. 用运行页面验证这些验收点，差异超过容差才生成问题卡。

因此，当前方案可以先不等待 Figma 权限，先用源站/批准版本完成比赛 MVP；Figma 作为增加说服力和扩展到“需求/设计验收”的第二阶段。

## 十三、比赛演示建议

建议准备一个可控的 Xspark 脱敏演示环境：

1. 先展示基线登记：页面、接口、操作和三种视口被收录。
2. 在目标版本中故意制造四个缺陷：移动端菜单隐藏、API 鉴权头错误、续费日期计算错误、解封状态链断开。
3. 一键执行验收，展示实时进度和覆盖率。
4. 打开问题卡，看到具体路由/接口、断言、截图差异、请求摘要、DB 对账和复现步骤。
5. 修改其中一个缺陷重新运行，报告显示该问题已修复，其余问题仍保持稳定。
6. 最后演示一个动态噪声和一个源站自身缺陷，说明它们被标记为环境差异或基线问题，而不是误报成目标 BUG。

这个演示比展示一个模糊的总分更能证明系统“自动验收”和“可定位、可复现”。

## 十四、边界和风险

- 只对自有或明确获授权的源站、测试环境和账号执行采集与验收。
- 登录态、Cookie、JWT、HAR、API 正文和数据库结果默认脱敏；证据包不能直接公开凭据或个人数据。
- 写操作默认阻断，只有精确白名单、独立测试账号和回滚方案同时存在时才允许执行。
- 动态第三方服务、随机数据、价格库存、时间和异步回调需要 fixture、mock 或归一化规则。
- 源站自身失败时，不把目标项目的同样结果直接判为目标缺陷。
- 高视觉分不能代表完整业务等价；报告必须分别展示四个维度、覆盖率和未执行项。
- Figma 权限不足时，不能声称已完成设计稿验收，只能说明 Mirror 模式已完成或使用了公开/导出的设计资产。

## 十五、后续可扩展方向

- 用 OpenAPI、PRD 表格和 Figma 元数据自动生成候选 `acceptance-point`，由人工批准后执行。
- 引入领域适配器：电商、后台管理、代理 IP、内容站和 SaaS 控制台共享同一验收编排层。
- 增加差异白名单的生命周期：临时批准、到期复核、版本绑定和审计记录。
- 将问题卡和覆盖清单接入 CI、Issue tracker 或代码审查，但默认只上传脱敏证据。
- 用模型做语义聚类、复现步骤润色和疑似根因排序；模型输出必须引用原始证据，不能替代断言执行。
- 形成基线质量分、目标质量分、修复前后差异和历史回归趋势，支持研发团队持续验收。

## 十六、建议的第一批落地任务

1. 在 Heimdall 中增加 `docs/competition` 方案和 `acceptance-point` 示例 fixture。
2. 设计 `baseline / target / oracle / normalization / evidence` 五个核心对象的 JSON schema。
3. 把现有 `verify`、`differ`、`interactions` 和离线 health 检查组合成 `accept` 命令的最小编排层。
4. 用两个本地站点 fixture 注入“目标 BUG”和“环境差异”，验证检出率与误报率。
5. 接入 Xspark 的五条脱敏验收点，先完成只读 API、页面和状态检查。
6. 再根据设计侧权限决定是否接入 Figma Frame；不把 Figma 权限作为 MVP 阻塞条件。

最终目标不是得到一个看似精确的“还原度百分比”，而是让每个通过、失败和待复核结论都有明确参照物、可重复步骤和可审计证据。
