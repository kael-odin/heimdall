# Spec 需求基线实施验收

日期：2026-10-16。范围：B2.1 完整 Spec 需求候选、预览、批准与独立选用。操作合同见[需求基线指南](../../competition/acceptance-baseline.md)，此前的[项目版本目录](acceptance-catalog.md)和[格式升级](acceptance-catalog-migration.md)保留为各自提交的历史证据。

## 用户可见结果

控制台在已选项目的“Spec 需求合同”区展示当前选用、候选、完整合同预览、批准及选用历史。候选从本项目已归属的 Spec 运行产生。预览显示完整来源、全部预期断言与 schema、规则和身份，批准和选用各自要求理由与确认。批准只增加历史，首次 current 仍为空；选用、取消及回退分别追加不可变记录。

完整未批准草稿没有 request / response 也可以供人复核；已完成但目标发现 BUG 的运行同样能提供正确需求。目标的实际响应不会进入 expected。原始门禁、计划、报告和证据保留；这些操作不发起新运行。所有新增响应均为 `executionReady:false`。

## 核心保护与本次修复

- 私有 materializer 用文件描述符固定预算读取 manifest、report 及全部引用证据，验证文件路径、身份、长度、当前 SHA 与 owner / 根；返回前二读核对。没有调用旧快照读取器的 stat 后无界 `readFileSync` 路径。
- 纯 projector 不信任历史 `integrity.valid` 或摘要字符串，独立验证原始 bytes、计划、报告汇总、完整槽位、证据角色、OpenAPI 来源及每项检查身份。完整合同超展示预算直接拒绝，不截断批准内容。
- 新摘要采用明确用途和版本的 canonical 哈希；原 plan / source / contract 指纹维持各自旧算法。规则版本按已审源码 LF / CRLF 两个原摘要显式识别，未知版本不默认为当前版本。
- candidate、approval 和 selection 的字段、引用、内容摘要、单事件关系及顺序链严格验证；current 从事件链推导，取消记录不会被界面当作仍有批准选用。
- 写入先双 CAS，再读取来源，并在 rolling previous 更新后、正式 head 发布前重验来源。独立审查实际复现了原先缺少最后一次复验的窗口：注入来源变化时原代码仍批准成功；修复后 create / approve / nonempty select 均拒绝且 head 不变。
- HTTP 只投影安全错误，严格路径与字段，沿用鉴权、no-store 和 16 KiB body 上限。项目详情只列存储摘要；单候选预览才装载来源。来源失效保留历史，取消选用独立于来源。
- 项目 / candidate / generation / revision 的迟到读取失效；POST 发出后不会因切项目而自动重发。409、无效成功响应和传输失败均清确认、保留理由、要求刷新核对已提交历史。

## 证据层级与剩余边界

本批的端到端证据使用本地只读 HTTP 夹具、真实引擎 worker、真实 Chromium 和当前文件系统。源码 / 文件系统故障注入覆盖更窄的时序与破坏条件，不能写成已经经历真实断电或任意恶意进程竞争。

已有归档 run 的读取演练只读验证旧材料，未重新访问旧夹具地址；它不能替代获授权的真实业务 API 验收。支持范围是当前规范化 Spec schema 与已审规则实现，未增加鉴权业务、写操作或任意 OpenAPI 完整覆盖。

目录仍不是签名审计账本。来源复验与 head 写入不是跨文件事务，不能绝对阻止管理员在最后检查后修改磁盘。rolling previous 可能在失败时已经前进，head 仍是唯一语义提交点；历史和前像不自动清理。

托管执行、Browser 所选侧来源锁、持久 BUG 工单与可靠关闭状态仍未实现。下一切片将把明确选用的 Spec 合同与明确目标版本接入执行，并保留批准、选用和目标版本的不可变来源关系；本批不提前声明这一能力。
