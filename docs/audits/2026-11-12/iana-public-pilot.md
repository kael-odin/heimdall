# IANA 公开站点试点：视觉验证通过，严格离线交付未通过

## 结论先说

2026-11-12，本机使用真实 Chromium 对公开站点 `https://www.iana.org/domains/example` 做了一个受限试点。Heimdall 在当前验证器修复后完成了 8/8 个已发现页面、24/24 个视口的视觉测量，平均分为 100%，最差视口仍为 A，`bounded=0`、`untested=0`、`blockers={}`。这证明当前多视口视觉验证链路能跑通。

但这不等于“整站离线复制成功”。同一次 `live --offline --strict` 导出仍因动态第三方资源、未捕获页面路径和浏览器离线探针未执行而失败。候选包已保留，正式旧包没有被覆盖。

证据分级：

- **真实流程**：真实 Chromium 访问 IANA、侦察、克隆、三视口视觉验证、严格导出命令。
- **源码确认**：验证器先切视口再注册请求监听器；挂起请求现在保留去敏诊断；测试覆盖旧视口响应式请求竞态。
- **离线交付**：候选包的 `health.json`、`verify-summary.json` 和导出退出码；它只能说明本次包的门禁结果。

## 修复了什么

之前验证器在连续切换视口时，旧页面的响应式 CSS 可能先发起资源请求。监听器把这类旧页面请求算进新视口的等待周期，最后把已经稳定的页面误判成还有挂起请求。

本轮修复做了两件事：

1. 先 `setViewportSize()`，再安装请求监听器并导航到目标页面；
2. `pendingRequests` 从 `Set` 改成 `Map`，失败时记录 origin、路径、资源类型、方法、同源性、HTTP 状态和挂起时长。

回归测试新增了“旧视口响应式请求不应阻塞新视口”的真实本地 HTTP 夹具，也补了挂起图片的诊断字段断言。专项 `core/test/verify-cli.test.mjs` 结果为 25/25 通过。

修复前 IANA 首页在桌面视口未完成；诊断最终定位到同源 CSS 背景图片 `iana-logo-homepage.3914c6f1ab9d.svg`，不是长轮询。修复后首页三种视口全部完整测量，整站复跑为 8/8 页、24/24 视口通过。

## `offline`、`heal`、`strict` 到底是什么意思

这三个参数不是一回事：

| 参数 | 实际含义 | 本次行为 |
| --- | --- | --- |
| `--offline` | 交付包运行时不允许回源；未命中的请求应失败或返回 404 | 候选包声明离线模式，但包本身仍需通过门禁 |
| `--heal` | 导出阶段允许访问原站，尝试补抓公开资源或页面 | 本次尝试 3 次，成功 1 次，失败 2 次；所以导出过程不是绝对断网 |
| `--strict` | 把未解析资源、站外资源、缺失路径和离线浏览器检查等纳入发布门禁 | 本次发现阻断后退出码为 1，旧正式包未覆盖 |

因此，“`--offline` 导出”准确说法是“最终包运行时离线”；要证明导出过程也完全不联网，必须在隔离网络环境中运行，并且不能使用 `--heal`。
