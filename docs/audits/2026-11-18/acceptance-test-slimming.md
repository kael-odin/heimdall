**这套测试里冗余很少，剩下的 1,100 多个顶层测试各自都还有独占的作用**。

## 怎么决定删哪个（四道闸）

1. **逐条覆盖**：给每个顶层测试单独跑一次，`NODE_V8_COVERAGE` 合并子进程（子进程被杀前每 400ms 落一次盘），得到它执行了哪些源码字符。
   1,237 个顶层测试里 1,190 个测到；其余 47 个（浏览器矩阵夹具、独立进程崩溃用例）直接保留，不参与分析。
2. **纯覆盖反删**：从最重的开始删，只有当它执行的每个字符都还有别的测试执行时才删——单这一道就有 346 个测试、约 4.5 千行“可删”。
3. **缺陷注入**：覆盖相等不等于检出力相等。在内存里给源码植入单算子缺陷（`node:module` 的 `registerHooks` 改写模块源码，磁盘上一个字节都不改），共 20,407 个，分布在 71 个验收源文件；
   对每个缺陷，先看要删的测试里谁检出，再确认留下的测试里也一定有人检出，否则保留最轻的那个检出者。这一道把 346 个可删压到 138 个。
   - 前 200 个缺陷的抽样试跑用来定参，随后全量跑完（51,521 次测试进程，约 2.4 小时）。
   - 每条“留下的测试能检出”在轻载下重跑复核；13 条复核不成立，重新评估。
4. **留出缺陷集**：用一整套不同的算子（`if` 取反、逻辑操作数单独留下、`await` 去掉、参数丢弃、数组/对象清空、`++/--` 互换等）
   另生成 13,532 个缺陷，分 1,200 + 1,200 + 9,632 三次抽检删除清单。第一组 553 个“被删测试检出”的缺陷里丢了 6 个 → 补回 6 个测试；第二组 3,980 个里补回 8 个；
   最终 0% 丢失。**这一道是最有价值的**：只用一套算子调出来的清单，换一套算子会漏掉约 1% 的检出力。
5. **共享代码复核**：覆盖率测量最初只盯 `core/src` 与 `console/src`，对 `core/scripts/` 与夹具里的代码是盲的。补测后发现有 15 个候选测试是
   `start-acceptance-demo.mjs`、`benchmark-acceptance.mjs`、`smoke-acceptance-demo-console.mjs` 和两个夹具的唯一执行者，全部保留。

最终清单：`selection/removed-keys.final.json`（107 个）。

## 减完的验证

- 改过的 37 个文件逐条重测：留下的 474 个测试全部通过；被执行的源码字符 1,310,323 → 1,310,979（多出的 656 个是执行路径的逐次差异），**没有任何一段因此不再被执行**。
- 本机：验收套件 1,642 / 1,652，0 失败，10 跳过；快速集 1,392 / 1,392；`lint` 774 文件；`check:frozen` 14 个文件未动。
- Hosted CI（提交 `21f733f7`）8 个作业全部通过；全量两分片合计 3,284 / 3,288 通过，0 失败，4 跳过。
- 被删测试提到的最新证据用例（例如“黄金投影”“1024 边界”）如果直接删掉就没有了——这是知道且接受的风险：留出缺陷集没有显示它们挡住过任何单算子缺陷，
  但它们挡的是“语义级”变化（比如常量换了一个值、整段逻辑换实现），单算子缺陷按定义测不到这一类。

## 这个方法的边界（不藏）

- 单算子缺陷只能证明“这行代码被改坏了会有人叫”；不能证明“行为被整体换掉还有人叫”。
- 只测了 Windows 本机：9 个删除候选因为自己写了 `process.platform` / 符号链接 / `skip` 分支而保留，Linux 上它们未必都可删。
- 覆盖率字符数相等 ≠ 断言相等：删掉的测试可能断言了别人执行到但没检查的细节。缺陷注入是对这一点的部分补偿，不是全部。
- 脚本与测量数据没有进仓库：它们是按需重跑的一次性工具，不是产品代码；方法写在本文，数据在仓库外归档。
